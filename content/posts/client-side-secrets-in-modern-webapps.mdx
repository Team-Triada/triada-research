## Why this keeps happening

Modern frontend stacks (React SPAs, Next.js static exports, Supabase/Firebase-backed apps) push more logic and more configuration into the browser bundle than the server-rendered apps of the previous decade. Developers reach for `.env` variables assuming a build step protects them, without distinguishing between variables meant for the **server** and variables meant to be **public by design**.

The result is a predictable class of finding, repeated across unrelated codebases: a signing key, an internal API secret, or an over-permissioned "anon" database key sitting in plaintext inside a `.js` bundle served to anyone who loads the page.

## Where to look

1. **Built JS bundles, not source.** Source repos are often private; the compiled `_next/static/chunks/*.js` or `assets/*.js` files are public by definition once the app is deployed. `grep` these directly.
2. **Environment variable naming conventions as a signal.** In Next.js, anything prefixed `NEXT_PUBLIC_` is intentionally bundled client-side, that's expected. The finding is when a variable *without* that prefix (or its equivalent in Vite/CRA) still ends up in the bundle because it was referenced from client-executed code.
3. **Third-party BaaS "anon" keys.** Supabase and Firebase both ship a public anon/client key by design, so that alone is not a bug. The bug is when Row-Level-Security (Supabase) or Firestore rules (Firebase) are missing or misconfigured, so the intentionally-public key grants unintended read/write access to tables that should be server-only.
4. **Signing keys mistaken for API keys.** The most severe version of this pattern: a key meant to *sign* requests (HMAC secret, JWT signing secret) shipped as if it were a public API key. Anyone holding it can forge valid signed requests, not just read data, which is a categorically worse outcome than a leaked read-only key.

## A practical triage flow

```bash
# 1. Fetch every JS asset referenced by the page (not just the entrypoint, check chunks too)
curl -s https://target.tld/ | grep -oE 'src="[^"]+\.js"'

# 2. Run a secret-pattern scanner against the concatenated bundle text,
#    not the minified single-line blob (some tools choke on files with no newlines)
trufflehog filesystem ./bundles --only-verified

# 3. For each candidate match, classify:
#    a. Intentionally public (anon key, publishable key) -> check the authorization
#       model behind it (RLS / Firestore rules / route guards), not the key itself.
#    b. Not intended for the client -> confirm the key is live before reporting,
#       to avoid false positives on rotated or placeholder values.

# 4. For live, non-public findings: determine blast radius by testing what the key
#    can DO, not just that it authenticates. Read-only access to a public table
#    is a different severity than write access to a users table.
```

## Severity is about the authorization model, not the leak

The recurring mistake in triage is treating "found a key in the bundle" as the finding. It isn't. The finding is what that key can *do* once an attacker has it. A Supabase anon key with tight RLS policies scoped to public, non-sensitive tables is expected behavior, not a vulnerability. The same anon key against a table with RLS disabled, letting anyone read and write user records, is a critical.

This distinction is what separates a useful report from a scanner-output dump: always chain the discovery to a demonstrated, bounded-impact PoC before scoring severity.

## Fix guidance for engineering teams

- Treat any credential that is not explicitly designed for public exposure as a server-only secret, full stop. Never reference it from client-executed code, even "just for local dev."
- For BaaS platforms (Supabase, Firebase, PocketBase), audit row-level security and rules as the actual security boundary. The anon key is not the boundary; the policy is.
- Rotate immediately on discovery, and audit access logs for the exposure window. Client-side secrets are often exposed far longer than server-side ones because nothing alerts on their presence in a public bundle.
